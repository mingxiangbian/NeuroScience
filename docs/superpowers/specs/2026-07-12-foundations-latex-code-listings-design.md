# Foundations LaTeX Code Listings Design

Date: 2026-07-12

Status: Approved design

## Context

Foundations knowledge articles now support structured Markdown, fenced code blocks and semantic article sections. The current presentation still has two related defects:

1. A numbered `核心机制` list breaks when an item starts with inline code. The list item is a two-column CSS Grid, so the generated `<code>` element and its following text become separate grid items. The code stretches across the content column while the remaining Chinese text may be auto-placed into the 42px marker column and wrap one character per line.
2. Inline code and fenced code share the same bordered white treatment. A fenced block therefore receives both the outer `pre` surface and the inner `code` background, creating an unattractive nested white box that conflicts with the rice-paper reader.

The change must fix the layout defect first, then introduce a reusable LaTeX `listings`-inspired code environment without redesigning the rest of the reader.

## Goals

- Keep numbered mechanism items readable when they contain inline code, links, emphasis or plain text.
- Give inline code and fenced code clearly different visual roles.
- Render fenced code as one restrained, paper-compatible listing with a language label, copy control and optional line numbers.
- Self-host IBM Plex Mono so code typography is stable across deployments.
- Preserve selectable code text, local highlights, local notes and plain-text copying.
- Support light theme, dark theme, desktop and mobile without page-level horizontal overflow.
- Keep Markdown as the only authored source.

## Non-goals

- No executable playground, terminal emulator or code editor.
- No copy control for inline code.
- No manually authored HTML for code listings.
- No automatic language guessing when a fenced block has no language class.
- No line wrapping inside fenced code.
- No redesign of module navigation, article prose, tables, process diagrams or the annotation panel.
- No external font CDN request.

## Root Cause And List Repair

The source Markdown is valid:

```markdown
1. `expected` 必须由产品 Policy 或行为契约导出，不能由当前实现反推。
```

`marked` correctly produces one list item containing an inline `<code>` element followed by a text node. The defect comes from applying Grid directly to the `li`.

The repaired mechanism list uses a normal block formatting context:

- `li` is `position: relative`, not Grid or Flex.
- A stable left padding reserves space for the numbered marker.
- `li::before` is absolutely positioned inside that reserved space.
- The generated inline content stays in one ordinary text flow.
- The marker remains inside the article reading edge and keeps the existing `01`, `02`, `03` format.
- Long content wraps only in the content area, never inside the marker column.

This is a CSS repair. It does not add wrapper elements to generated Markdown and does not change `roadmap-data.json`.

## Code Typography

### Self-hosted font

Fenced and inline code use IBM Plex Mono before the existing system fallbacks.

Required assets:

- IBM Plex Mono Regular, WOFF2
- IBM Plex Mono Medium, WOFF2
- the corresponding SIL Open Font License notice

The font is loaded with local `@font-face` declarations and `font-display: swap`. The code stack ends with the existing system monospace stack and Chinese system fallbacks, so Chinese comments remain readable when IBM Plex Mono has no glyph.

No Google Fonts or other remote font request is allowed.

### Inline code

Inline code is part of prose, not a miniature code panel.

It uses:

- IBM Plex Mono at approximately `0.88em`
- medium weight
- a subtle green-gray tint derived from the existing reader palette
- compact horizontal padding
- a maximum 3px radius
- no border
- no pure-white background
- normal inline flow and normal wrapping opportunities around the token

Inline code must never stretch to the width of a list, paragraph or table cell.

### Fenced code

A fenced block becomes one `.code-listing` environment with this hierarchy:

```text
code-listing
  code-listing-header
    language-label
    copy-button
  code-listing-body
    optional-line-number-gutter
    pre
      code
```

The listing uses:

- one thin ink-tinted outer border
- a paper-compatible green-gray surface, not pure white
- a slightly differentiated header surface
- 6px outer radius
- no decorative card shadow
- IBM Plex Mono at approximately 13 to 14px
- line height around 1.65
- stable padding around code
- horizontal scrolling inside the code body when required

The nested `pre > code` resets border, background, radius and padding. Only the outer listing defines the visual frame.

## Language Label And Copy Interaction

The language label comes from the fenced-code class generated by Markdown, such as `language-python`.

- Known language text is displayed in uppercase, such as `PYTHON` or `TYPESCRIPT`.
- A block without a language class displays `CODE`.
- The label is ordinary header text, not a floating pill.

The copy control is an icon-only button using the Lucide Copy icon and an accessible Chinese label.

On activation:

1. Copy the original plain code text without line numbers or language text.
2. Replace Copy with the Lucide Check icon for approximately 1.5 seconds.
3. Change the accessible label to indicate success during that interval.
4. Restore the original icon and label without moving surrounding layout.

If clipboard access fails, keep the Copy icon, expose a failure label to assistive technology and do not display a blocking modal. Keyboard activation and a visible focus state are required.

## Line Numbers

Line numbers appear only when the normalized code contains four or more logical lines.

- One to three lines: no gutter.
- Four or more lines: show a fixed-width gutter starting at `1`.
- A single trailing newline inserted by Markdown does not create an extra displayed line.
- Numbers are presentation only, use `aria-hidden="true"` and are excluded from selection and copying.
- Code does not wrap, so each gutter number remains aligned with one logical source line.
- Horizontal scrolling moves the code, while the number gutter remains visually anchored.

The implementation should create a separate number gutter rather than injecting selectable numbers into the `<code>` text.

## Syntax Highlighting

Syntax highlighting is performed at build time with `highlight.js`. The builder imports the core package and explicitly registers the language grammars used by Foundations: Python, JavaScript, TypeScript, Rust, JSON, Bash, YAML and Markdown. It calls the explicit-language API rather than `highlightAuto`, so output is deterministic and the browser loads no highlighting runtime. The implementation follows the official `highlight(code, { language, ignoreIllegals })` API and preserves the library's safe-mode fallback.

Rules:

- Highlight only when the fenced block declares a supported language.
- Unsupported or absent languages remain escaped plain code.
- The sanitizer adds `span` and permits only the `hljs-*` classes emitted by `highlight.js`.
- Raw HTML from Markdown remains unable to add arbitrary highlight classes or executable content.
- The generated spans must not change `textContent`, copied text or annotation matching.

The palette is intentionally restrained:

- keywords and built-ins: reader blue-green
- strings and numeric literals: muted ochre
- comments: muted ink-green
- function and type names: deep ink with medium weight
- punctuation and ordinary identifiers: normal code ink

The listing must remain understandable without color, and both themes must maintain readable contrast.

## Runtime Enhancement Order

The Markdown build continues to emit sanitized `<pre><code class="language-*">...</code></pre>` content. The reader enhances these blocks after inserting the current module HTML and before restoring annotations.

For every block, the enhancer:

1. Reads and stores the original plain code text.
2. Extracts the declared language.
3. Wraps the existing `pre` in the listing structure.
4. Adds the language label and copy button.
5. Adds a separate line-number gutter only when the four-line threshold is met.
6. Leaves the code text itself unchanged.

Enhancement must be idempotent. Re-rendering a module or restoring Mermaid content cannot wrap an existing listing a second time.

## Annotation Compatibility

Code remains part of the knowledge article's selectable content.

- Users can select code and create the existing highlight or note annotation.
- Language labels, copy controls and line numbers are excluded from annotation creation.
- Restoring an annotation must resolve against the original code text after listing enhancement.
- Copying uses stored source text, not the listing container's combined `textContent`.
- Existing prose annotations continue to resolve because the mechanism-list repair does not alter authored text.

No local annotation storage schema changes are required.

## Responsive And Theme Behavior

### Desktop

- The listing fills the article text width, not the viewport width.
- Header and gutter dimensions remain stable when code scrolls.
- Long code scrolls inside `pre` and cannot widen `.reader-main`.

### Mobile

- The same listing structure remains visible.
- Outer padding and gutter width reduce slightly.
- Code font does not scale with viewport width.
- Horizontal scrolling remains inside the code area.
- The copy button retains at least a 40px touch target.

### Dark theme

- Keep the same hierarchy and spacing.
- Replace the light paper fill with a dark ink-tinted surface.
- Avoid pure black and high-saturation editor colors.
- Inline code remains quieter than a fenced listing.

## Testing And Acceptance

### Mechanism-list regression

- The first Eval mechanism item renders `expected` and its following sentence in one normal text flow.
- No Chinese sentence wraps one character per line in the marker column.
- Inline code does not stretch across the available row.
- The `01` to `04` markers remain aligned and inside the reading edge.
- The same behavior holds at desktop and mobile widths.

### Inline code

- Inline code has no border and no pure-white background.
- It uses IBM Plex Mono when the font asset loads.
- Inline code inside paragraphs, lists and table cells does not change parent layout.

### Fenced code

- A Python fence displays `PYTHON`, one outer frame and one copy button.
- `pre > code` has no independent frame or fill.
- Three lines show no gutter; four lines show line numbers `1` through `4`.
- A trailing newline does not add a false fifth number.
- Long lines scroll inside the listing without causing page overflow.
- Unsupported languages fall back to readable escaped plain code.

### Copy behavior

- Copy output exactly matches the original code text and excludes line numbers and language text.
- Mouse and keyboard activation work.
- Success changes the icon to Check without layout shift, then restores it.
- Clipboard failure does not throw an uncaught error or open a modal.

### Annotation behavior

- A code selection can be highlighted and restored after reload.
- A code selection can receive a local note.
- Controls and line numbers cannot become annotation text.
- Existing article annotations still resolve after the change.

### Visual verification

Verify at minimum:

- `Evals & Debugging / Eval Case 的六层结构 / 核心机制`
- the Python blocks in `逐步示例`
- desktop around 1440px wide
- mobile around 390px wide
- light and dark themes

The final screenshots must show no single-character vertical wrapping, no nested white code box, no overlapping header controls and no page-level horizontal scrollbar.

## Rollout Boundary

This change ends when the mechanism-list regression is fixed, the reusable listing treatment is active for existing fenced code, IBM Plex Mono is self-hosted, copy and conditional line numbers work, syntax highlighting is sanitized, and focused tests plus desktop/mobile screenshots pass.

It does not migrate additional learning content or redesign unrelated Foundations components.
